# minio

Объектное хранилище happydebt.

| Бакет | Что лежит | Диск CRM | Переменная в `.env` CRM |
|---|---|---|---|
| `registry` | реестры должников, выгрузки отчётов (`reports/*`) | `s3` (он же `FILESYSTEM_DISK`) | `AWS_BUCKET` |
| `record` | записи разговоров | `s3records` (только чтение; пишет telephony-ari) | `AWS_RECORDS_BUCKET` |
| `whatsapp` | файлы и голосовые переписки WhatsApp | `s3whatsapp` | `AWS_WHATSAPP_BUCKET` |
| `documents` | документы должников | `s3documents` | `AWS_DOCUMENTS_BUCKET` |
| `chat-attachments` | вложения и голосовые внутреннего чата операторов (HAP-528) | `s3chat` (HAP-531) | `AWS_CHAT_BUCKET` |

Список закрыт: это все бакеты, в которые ходит хоть один сервис через **это** хранилище
(аудит HAP-535 по crm, file_service, crosschat, payment_service, sockets-go,
telegram_user_api, WAHA, homebank_pull_info, bailiff_aisoip). Заводить бакет = добавить его
в `MINIO_BUCKETS`/`MINIO_CRM_BUCKETS` здесь **и** проверить `.env` целевого хоста — почему
одного репозитория пока не хватает, разобрано в разделе «Список бакетов задан в ДВУХ
местах».

⚠️ **В `documents` теперь пишет и file_service (HAP-620).** Раньше это был пустой бакет под
диск `s3documents` CRM, а файлы сервиса лежали в его собственном MinIO — в бакете с тем же
именем. После консолидации хранилище одно и бакет один; подробности и цена решения — в
разделе «Консолидация file_service (HAP-620)».

⚠️ **Бакета `records` (с «s») здесь нет и не должно быть** — см. «Записи бота» ниже.

## Запуск

```bash
cp .env.example .env
$EDITOR .env                 # обязательно: MINIO_ROOT_USER, MINIO_ROOT_PASSWORD
chmod 600 .env
docker network create local-network   # если сети ещё нет (она общая, external)
docker compose up -d
```

Данные — в `./data` рядом с этим файлом. Бакеты создаются автоматически при старте
(сервис `minio-init`, отрабатывает и завершается с кодом 0 — это норма).

| Что | Адрес по умолчанию |
|---|---|
| S3 API | `:9000` |
| Веб-консоль | `:9001` |

## 🔴 Миграция с именованного volume

Раньше данные лежали в volume `minio_data`, теперь — в каталоге `./data`. **Сами они не
переедут**: после переключения MinIO увидит пустой каталог и заведёт хранилище с нуля.
Для хранилища с записями разговоров и файлами WhatsApp это означает, что старые объекты
перестанут отдаваться, хотя сам сервис поднимется как ни в чём не бывало.

Порядок переноса на работающей установке:

```bash
cd <каталог с docker-compose.yml>
docker compose down

# 1. Убедиться, что старый volume на месте и найти его точку на диске
docker volume ls | grep minio_data
SRC=$(docker volume inspect -f '{{ .Mountpoint }}' <имя_volume>)

# 2. Скопировать содержимое (rsync сохраняет права и время)
sudo rsync -aH --info=progress2 "$SRC"/ ./data/

# 3. Сверить объём — числа должны совпасть
sudo du -sh "$SRC" ./data

docker compose up -d
```

Старый volume после проверки **не удаляйте сразу** — пусть полежит как страховка, пока
не убедитесь, что всё отдаётся.

## Что изменилось и почему

**`MINIO_DEFAULT_BUCKETS` убрана — она не работала.** Это переменная образа `bitnami/minio`,
а используется официальный `minio/minio`, который её игнорирует. Проверено 10.08.2026:
запуск с `MINIO_DEFAULT_BUCKETS=registry,record,whatsapp` дал ноль бакетов. То есть бакеты
всё это время заводились руками, а конфиг создавал впечатление автоматизации. Теперь их
создаёт сервис `minio-init` — идемпотентно, существующие данные не трогает.

**Версия образа зафиксирована** вместо `latest`: обновление хранилища должно быть
осознанным действием через PR, а не побочным эффектом `docker compose pull`.

**Дефолты `minioadmin/minioadmin` убраны.** Дефолтный пароль у админки хранилища рано или
поздно уезжает в прод — достаточно один раз запустить без параметров. Теперь без
`MINIO_ROOT_USER`/`MINIO_ROOT_PASSWORD` в `.env` compose просто не стартует.
Ограничения MinIO: логин ≥ 3 символов, пароль ≥ 8, иначе контейнер падает при старте.

**Добавлен healthcheck** — без него создание бакетов начиналось раньше, чем сервер
принимал соединения.

## Сервисный аккаунт CRM (HAP-509)

CRM ходит в это хранилище **root-кредами** — `hd-minio-admin` лежит и в `minio/.env`, и в
`crm/.env`. Значит, тот, кто катит CRM, владеет хранилищем целиком: записями разговоров,
файлами WhatsApp, реестрами. Никакая изоляция credentials в Jenkins этого не меняет, пока
секрет физически один и тот же.

Лечение — узкая учётка рядом с root'ом. Её заводит `_docker/init.sh` при каждой выкатке:

* пользователь `MINIO_CRM_ACCESS_KEY` с политикой `crm-app`;
* политика перечисляет действия явно (чтение/запись/удаление объектов, multipart, листинг
  бакета) и **только** на бакеты из `MINIO_CRM_BUCKETS`. Ни создания бакетов, ни удаления,
  ни admin-действий. Встроенная `readwrite` не годится: это `s3:*` на `arn:aws:s3:::*` —
  ровно то, от чего мы уходим;
* всё идемпотентно: повторный прогон перезаписывает политику своим же содержимым и
  выравнивает секретный ключ пользователя. Аккаунт переживает `docker compose down && up`,
  потому что описан кодом, а не заведён руками в консоли.

**Ключи в `.env` руками не пишутся.** Источник — Credentials Store папки `crm` в Jenkins
(`crm-minio-access-key`, `crm-minio-secret-key`), разносит их выкатка через `envSecrets`
(см. `jenkins-infra/DEPLOY.md` §10). Ротация = поменять значение на контроллере
(`secrets/crm_minio_*`), `stack.sh reload`, выкатить `minio` и `crm`. Копипаста между
`.env` разных сервисов и была причиной того, что один секрет оказался в трёх местах.

Пустые `MINIO_CRM_*` — не ошибка: аккаунт не заводится, бакеты создаются как обычно. Это
нужно, чтобы стек поднимался на машине, где ключи ещё не разложены.

🟡 `MINIO_CRM_BUCKETS` обязан совпадать с `AWS_BUCKET` / `AWS_RECORDS_BUCKET` /
`AWS_WHATSAPP_BUCKET` / `AWS_CHAT_BUCKET` в окружении CRM. Расхождение выглядит как
`AccessDenied` на ровном месте, поэтому список меняется согласованно с `crm-backend`.

Проверить, что учётка действительно узкая:

```bash
docker run --rm --network local-network -it minio/mc:RELEASE.2025-04-16T18-13-26Z sh
mc alias set crm http://minio:9000 <access-key> <secret-key>
mc ls crm                      # только свои бакеты
mc mb crm/proba                # AccessDenied — новых бакетов заводить нельзя
mc admin info crm              # AccessDenied — admin-прав нет
```

## Недостающие бакеты: chat-attachments и documents (HAP-535)

Задача начиналась с одного бакета под чат, но аудит всех потребителей показал, что
хранилище отстаёт от кода ещё в одном месте. Добавлены оба.

### `chat-attachments` — вложения и голосовые внутреннего чата (HAP-528)

Подключается в CRM отдельным диском `s3chat` (HAP-531).

**Новых ключей нет — и это осознанно.** Учётка здесь заводится на *сервис*, а не на бакет,
а потребитель у чата ровно один: CRM сама принимает файл и сама стримит его участникам
чата, наружу ключи не уходят. Поэтому `chat-attachments` просто добавлен в
`MINIO_CRM_BUCKETS` — политика `crm-app` покрывает его тем же набором действий. Отдельная
пара ключей добавила бы третий секрет к ротации, ничего при этом не изолировав: обе учётки
жили бы в одном процессе PHP.

**Отдельный бакет, а не подпапка в `registry`** — потому что бакет это единственная
граница, которую понимают наши политики: префиксных прав в них нет. Сложив чат в `registry`,
мы бы выдали чату доступ к реестрам должников и наоборот.

`s3:DeleteObject` у CRM на этом бакете есть — в отличие от телефонии. Удаление сообщения с
вложением должно уносить и объект, иначе бакет копит осиротевшие файлы, на которые уже
никто не сошлётся.

Что нужно дописать в `.env` CRM (значения ключей и endpoint уже там — их приносит выкатка,
диск переиспользует те же `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` / `AWS_ENDPOINT`,
как `s3records` и `s3whatsapp`):

```dotenv
AWS_CHAT_BUCKET=chat-attachments
```

### `documents` — диск `s3documents` CRM, который указывал в никуда

Диск `s3documents` есть в `crm/config/filesystems.php` и объявлен в OpenAPI CRM как
допустимое значение параметра `?disk=` у `GET /files/{path}`. Бакета под него в хранилище
не было ни одного дня: имя `documents` осталось в устаревшем `crm/.env.example` и не
доехало ни до актуального `crm/env.example`, ни сюда. То есть `AWS_DOCUMENTS_BUCKET` пуста,
а диск бьёт в пустое имя бакета.

Тот же класс, что расхождение `record` / `records` из HAP-510: конфиг делает вид, что
хранилище настроено, а на деле запрос падает. Бакет заводим — это дешевле, чем выяснять,
кто из клиентов уже шлёт `?disk=s3documents`.

🟡 Чтобы диск заработал, `crm-backend` должен дописать в `env.example` и в `.env` на хосте:

```dotenv
AWS_DOCUMENTS_BUCKET=documents
```

Без этой строки бакет просто будет стоять пустым — вреда нет, пользы тоже.

⚠️ Не путать с бакетом `documents` сервиса `file_service`: у того **своё** хранилище MinIO
(контейнер `storage`, отдельный volume и сеть, наружу не публикуется). Имена совпадают,
данные не пересекаются.

### 🔴 Записи бота: бакет `records` заводить НЕ надо, надо чинить имя

CRM передаёт телефонии имя бакета для записей бота параметром `bot_records_bucket`
(`config/telephony.php`). Значения там сейчас такие:

| Откуда | Значение |
|---|---|
| `crm/env.example` | `records` |
| дефолт в `config/telephony.php` | `bot.records` |
| фактический бакет записей | `record` |

Три имени на одну сущность. Соблазн «завести все используемые бакеты» разбивается здесь о
то, что `records` и `bot.records` — не бакеты, а опечатки, и создание их сделает хуже:
записи бота лягут отдельно от остальных, а CRM отдаёт запись оператору через диск
`s3records` (`CallController::getRecord`), который смотрит **только** в `record`. Файл
будет существовать и при этом не открываться — молчаливо, без ошибки.

Правильная починка — на стороне CRM: `BOT_RECORDS_BUCKET=record` и такой же дефолт в
`config/telephony.php`. Это ровно тот вывод, к которому пришёл HAP-516 («расхождение
чинится на стороне потребителя, а не расширением политики»).

🔴 Побочно: после HAP-516 телефония ходит узкой учёткой с политикой только на `record`,
и права заводить бакеты у неё нет. Значит запись разговоров бота сейчас, скорее всего,
падает с `AccessDenied` — раньше root молча создавал `records` при первой загрузке. Стоит
проверить логи телефонии, прежде чем считать это косметикой.

### ⚠️ Список бакетов задан в ДВУХ местах, и хостовое побеждает

Дефолты в `docker-compose.yml` (`${MINIO_BUCKETS:-...}`) применяются, только когда
переменной нет в `.env` **целевого хоста**. `composeDeploy` подменяет в `.env` лишь
`envSecrets` (ключи сервисных аккаунтов) — списки бакетов он не трогает и не сверяет.
Значит любая строка `MINIO_BUCKETS=` в хостовом `.env` замораживает набор бакетов на том
значении, каким его когда-то скопировали из `.env.example`, и правки в этом репозитории до
хранилища не доезжают. Так и получилось, что `documents` не существовал.

Фактическое состояние `vm-stage` (сверено 14.08.2026):

| Переменная | В хостовом `/srv/minio/.env` | Что реально применяется |
|---|---|---|
| `MINIO_BUCKETS` | `registry,record,whatsapp` | **хостовое** — дефолт репозитория не работает |
| `MINIO_CRM_BUCKETS` | строки нет | дефолт репозитория |

Отсюда неочевидное следствие: **новые бакеты всё-таки создаются одной выкаткой** — но не
верхним циклом по `MINIO_BUCKETS`, а внутри `provision_account`, который перед выдачей прав
делает `mc mb --ignore-existing` на каждый бакет из `MINIO_CRM_BUCKETS`. То есть сейчас
набор бакетов хранилища де-факто определяет список CRM, а `MINIO_BUCKETS` — мёртвая строка.

🔴 Полагаться на это нельзя. Работает оно ровно потому, что `MINIO_CRM_BUCKETS` на этом
хосте не задана; `.env.example` её содержит, поэтому на хосте, разложенном по инструкции
(или на будущем проде), список окажется закреплён и механизм отвалится молча. Устранение
этой развилки — отдельная задача, варианты обсуждаются; до её закрытия при добавлении
бакета проверяйте хостовый `.env` глазами:

```bash
cd /srv/minio && grep -E '^MINIO_(CRM_)?BUCKETS=' .env
# Если строка есть и она короче списка из этого репозитория — правьте её,
# предварительно сняв копию: cp .env .env.bak-$(date +%F) (в .env лежат root-креды).
```

`minio-init` идемпотентен и гоняется на каждой выкатке: недостающее создаст, существующее
и его содержимое не тронет. Руками в веб-консоли бакеты заводить не нужно — заведённые
кликами они не описаны кодом и не видны в ревью.

Проверка после выкатки:

```bash
docker compose logs minio-init | grep -E 'bucket ready|policy ready'
# ожидаем 5 строк bucket ready и policy ready: crm-app -> ...,documents,chat-attachments
mc ls crm   # под учёткой CRM видны все пять
```

## Сервисный аккаунт телефонии (HAP-516)

Та же история, что с CRM, и обнаружилась она позже: `telephony-ari` тоже ходил в хранилище
**администратором** — в его `.env.secrets` лежали `hd-minio-admin` и значение, побайтово
совпадающее с `MINIO_ROOT_PASSWORD` (сверено по sha256 13.08.2026). А складывает он туда
записи разговоров. Пока root оставался у потребителя, его нельзя было и ротировать:
ротация ломала бы запись и выдачу разговоров, поэтому HAP-517 ждал именно этой задачи.

Учётку заводит тот же `_docker/init.sh`: пользователь `MINIO_TELEPHONY_ACCESS_KEY` с
политикой `telephony-ari` на бакеты из `MINIO_TELEPHONY_BUCKETS`. Права ýже, чем у CRM, и
это не осторожность ради осторожности, а список того, что реально делает клиент
(`workers/file_service/minio_client.py`): `bucket_exists` → `s3:ListBucket`, `fput_object`
→ `s3:PutObject` + multipart, плюс `s3:GetObject` — записи забирает STT-воркер, которому
эти же ключи уезжают в задании.

🔴 **`s3:DeleteObject` не выдан сознательно.** Удаления объектов в коде телефонии нет
вовсе, а запись разговора — ПДн и единственный экземпляр. Право удалить её не нужно тому,
кто её создаёт.

🔴 **Создания бакетов тоже нет, и это меняет поведение.** Клиент при первой загрузке
делает `make_bucket`, если бакета не оказалось. Под root это молча создавало бакет с
опечаткой в имени вместо ошибки — так и появилась путаница `record` / `records`
(в `deploy/.env` телефонии `MINIO_BUCKET=record`, а в коде воркеров имя `records`
захардкожено; бакета `records` в хранилище нет). Под узкой учёткой промах по имени станет
внятным `AccessDenied` — это то, чего мы хотим. Расхождение чинится на стороне
`telephony-ari`, а не расширением политики.

**Ключи в `.env` руками не пишутся** — источник тот же, Credentials Store папки `crm`
(`minio-telephony-access-key`, `minio-telephony-secret-key`). ⚠️ У этой пары два конца:
те же значения лежат в credential'е `telephony-ari-staging-env` папки `telephony`, откуда
их получает сам сервис. Ротация меняет **оба** — порядок в `jenkins-infra/DEPLOY.md` §10.

## Консолидация file_service (HAP-620)

У файлового сервиса было **своё** хранилище — контейнер `file-s3` (MinIO) в его
`docker-compose.yml`, со своим volume и своей сетью. Рекомендация architect-orchestrator
(HAP-609, согласована владельцем): консолидировать на этом инстансе. Раздельность давала
не изоляцию, а второй цикл патчинга, бэкапа и мониторинга — **на той же машине и том же
диске**: `minio` и `file-s3` оба крутятся на `vm-stage`, данные обоих лежат на `/` (LVM
`ubuntu--vg-ubuntu--lv`). Граница данных проходит по бакету и политике, а не по числу
процессов.

Проверка запаса перед переездом (19.08.2026, `vm-stage`):

| Что | Значение |
|---|---|
| `/srv/minio/data` (это хранилище, все бакеты) | 800 KB |
| volume `file_service_storage_data` (хранилище file_service) | 224 KB, из них бакет `documents` — 44 KB |
| Свободно на `/` | 52 GB из 96 GB (занято 43 %) |

То есть конкуренции за диск и throughput при переезде не возникает: переносимый объём —
десятки килобайт, оба инстанса и так делят один шпиндель, и после decommission `file-s3`
на хосте станет на один MinIO меньше.

**Бакет — общий `documents`.** Сначала заводился отдельный `file-service` (изоляция по
бакету), но владелец выбрал общий: фронт скачивает документы старым путём
`GET /api/download/{file_path}?disk=s3documents`, то есть читает именно `documents`, а ключ
объекта у file_service совпадает с `file_path` из ответа CRM. В общем бакете скачивание
работает сразу — не дожидаясь мержа HAP-609 (CRM проксирует байты из API сервиса) и
HAP-616 (фронт переходит на `id` файла).

⚠️ **Цена решения.** `documents` входит в `MINIO_CRM_BUCKETS`, а политика `crm-app` даёт
запись и **удаление**: CRM технически может удалить документ должника мимо владельца
данных. Изоляции по бакетам в этом варианте нет — граница осталась только на уровне
приложения. Вернуться к отдельному бакету = поменять `MINIO_FILES_BUCKETS` здесь и
`STORAGE_BUCKET` у file_service, но тогда фронт ждёт HAP-609/616.

Политика `file-service` — чтение, запись и удаление объектов в этом бакете плюс multipart и
листинг. `s3:DeleteObject` в отличие от телефонии выдан: `DELETE /api/v1/files/{id}` обязан
уносить и объект, иначе бакет копит осиротевшие файлы с ПДн — это нарушение минимизации, а
не экономия.

🔴 **Отдельно проверьте `GET /api/public/download/{path}?disk=s3documents` в CRM.** На стенде
он отдаёт байты объекта **без авторизации** и доступен снаружи (проверено 19.08.2026
запросом с чужой машины по `https://vm-stage.happydebt.kz/...`). Пока `documents` был пуст,
это ничего не значило; теперь через него достаётся документ должника, если известен путь.
Эндпоинт живёт в CRM, чинится там же — задача не этого репозитория, но знать о ней надо.

**Срок хранения (`MINIO_FILES_EXPIRE_DAYS`) намеренно пуст.** Retention документов должников
и записей разговоров — разные регламенты, и дефолт общего инстанса тут не образец; но
придумывать число вместо регламента нельзя: удаление необратимо. Механизм готов, включение
— одна переменная. Правила на брошенные multipart-загрузки в lifecycle нет: MinIO такое
действие не принимает вовсе (проверено 19.08.2026 — `did not validate against our published
schema`, флага нет и в `mc ilm rule add`), а убирает их сам — `mc admin config get local api`
показывает `stale_uploads_expiry=24h`, `stale_uploads_cleanup_interval=6h`.

Порядок самого переезда (перенос объектов, переключение конфига, окно отката и
decommission `file-s3`) описан в репозитории file_service: `plans/003-minio-consolidation.md`.

## Получение Access key / Secret key

Для нового сервиса — не руками в консоли: аккаунт, заведённый кликами, исчезнет при
пересоздании стека и не будет виден в ревью. Заводите его в `_docker/init.sh` по образцу
CRM (пользователь + своя политика на свои бакеты), а значения доставляйте выкаткой.

Если ключ всё же нужен разово (разбор инцидента, миграция данных):

1. Открыть веб-консоль (`:9001`), войти под `MINIO_ROOT_USER`.
2. Access Keys → создать ключ.
3. Регион уже задан через `MINIO_REGION` (`kz-ala-dev`) — в консоли менять не нужно.

⚠️ Регион менять на работающем хранилище нельзя без согласования: клиенты S3 подписывают
им запросы, и подпись разъедется у всех, кто уже настроен.

## Доступ к консоли

По умолчанию консоль слушает все интерфейсы — как было раньше. Если хост виден за пределами
доверенной сети, безопаснее закрыть её и ходить туннелем:

```bash
# в .env
MINIO_CONSOLE_BIND=127.0.0.1
# с рабочей машины
ssh -L 9001:127.0.0.1:9001 prog@<хост>
```
