# minio

Объектное хранилище happydebt. Бакеты: `registry`, `record`, `whatsapp`.

## Запуск

```bash
cp .env.example .env
$EDITOR .env                 # обязательно: MINIO_ROOT_USER, MINIO_ROOT_PASSWORD
chmod 600 .env
docker network create local-network   # если сети ещё нет (она общая, external)
docker compose up -d
```

Данные — в `./data` рядом с этим файлом. Бакеты создаются автоматически при старте
(сервис `minio-init`, отрабатывает и завершается с кодом 0 — это норма).

| Что | Адрес по умолчанию |
|---|---|
| S3 API | `:9000` |
| Веб-консоль | `:9001` |

## 🔴 Миграция с именованного volume

Раньше данные лежали в volume `minio_data`, теперь — в каталоге `./data`. **Сами они не
переедут**: после переключения MinIO увидит пустой каталог и заведёт хранилище с нуля.
Для хранилища с записями разговоров и файлами WhatsApp это означает, что старые объекты
перестанут отдаваться, хотя сам сервис поднимется как ни в чём не бывало.

Порядок переноса на работающей установке:

```bash
cd <каталог с docker-compose.yml>
docker compose down

# 1. Убедиться, что старый volume на месте и найти его точку на диске
docker volume ls | grep minio_data
SRC=$(docker volume inspect -f '{{ .Mountpoint }}' <имя_volume>)

# 2. Скопировать содержимое (rsync сохраняет права и время)
sudo rsync -aH --info=progress2 "$SRC"/ ./data/

# 3. Сверить объём — числа должны совпасть
sudo du -sh "$SRC" ./data

docker compose up -d
```

Старый volume после проверки **не удаляйте сразу** — пусть полежит как страховка, пока
не убедитесь, что всё отдаётся.

## Что изменилось и почему

**`MINIO_DEFAULT_BUCKETS` убрана — она не работала.** Это переменная образа `bitnami/minio`,
а используется официальный `minio/minio`, который её игнорирует. Проверено 10.08.2026:
запуск с `MINIO_DEFAULT_BUCKETS=registry,record,whatsapp` дал ноль бакетов. То есть бакеты
всё это время заводились руками, а конфиг создавал впечатление автоматизации. Теперь их
создаёт сервис `minio-init` — идемпотентно, существующие данные не трогает.

**Версия образа зафиксирована** вместо `latest`: обновление хранилища должно быть
осознанным действием через PR, а не побочным эффектом `docker compose pull`.

**Дефолты `minioadmin/minioadmin` убраны.** Дефолтный пароль у админки хранилища рано или
поздно уезжает в прод — достаточно один раз запустить без параметров. Теперь без
`MINIO_ROOT_USER`/`MINIO_ROOT_PASSWORD` в `.env` compose просто не стартует.
Ограничения MinIO: логин ≥ 3 символов, пароль ≥ 8, иначе контейнер падает при старте.

**Добавлен healthcheck** — без него создание бакетов начиналось раньше, чем сервер
принимал соединения.

## Сервисный аккаунт CRM (HAP-509)

CRM ходит в это хранилище **root-кредами** — `hd-minio-admin` лежит и в `minio/.env`, и в
`crm/.env`. Значит, тот, кто катит CRM, владеет хранилищем целиком: записями разговоров,
файлами WhatsApp, реестрами. Никакая изоляция credentials в Jenkins этого не меняет, пока
секрет физически один и тот же.

Лечение — узкая учётка рядом с root'ом. Её заводит `_docker/init.sh` при каждой выкатке:

* пользователь `MINIO_CRM_ACCESS_KEY` с политикой `crm-app`;
* политика перечисляет действия явно (чтение/запись/удаление объектов, multipart, листинг
  бакета) и **только** на бакеты из `MINIO_CRM_BUCKETS`. Ни создания бакетов, ни удаления,
  ни admin-действий. Встроенная `readwrite` не годится: это `s3:*` на `arn:aws:s3:::*` —
  ровно то, от чего мы уходим;
* всё идемпотентно: повторный прогон перезаписывает политику своим же содержимым и
  выравнивает секретный ключ пользователя. Аккаунт переживает `docker compose down && up`,
  потому что описан кодом, а не заведён руками в консоли.

**Ключи в `.env` руками не пишутся.** Источник — Credentials Store папки `crm` в Jenkins
(`crm-minio-access-key`, `crm-minio-secret-key`), разносит их выкатка через `envSecrets`
(см. `jenkins-infra/DEPLOY.md` §10). Ротация = поменять значение на контроллере
(`secrets/crm_minio_*`), `stack.sh reload`, выкатить `minio` и `crm`. Копипаста между
`.env` разных сервисов и была причиной того, что один секрет оказался в трёх местах.

Пустые `MINIO_CRM_*` — не ошибка: аккаунт не заводится, бакеты создаются как обычно. Это
нужно, чтобы стек поднимался на машине, где ключи ещё не разложены.

🟡 `MINIO_CRM_BUCKETS` обязан совпадать с `AWS_BUCKET` / `AWS_RECORDS_BUCKET` /
`AWS_WHATSAPP_BUCKET` в окружении CRM. Расхождение выглядит как `AccessDenied` на ровном
месте, поэтому список меняется согласованно с `crm-backend`.

Проверить, что учётка действительно узкая:

```bash
docker run --rm --network local-network -it minio/mc:RELEASE.2025-04-16T18-13-26Z sh
mc alias set crm http://minio:9000 <access-key> <secret-key>
mc ls crm                      # только свои бакеты
mc mb crm/proba                # AccessDenied — новых бакетов заводить нельзя
mc admin info crm              # AccessDenied — admin-прав нет
```

## Сервисный аккаунт телефонии (HAP-516)

Та же история, что с CRM, и обнаружилась она позже: `telephony-ari` тоже ходил в хранилище
**администратором** — в его `.env.secrets` лежали `hd-minio-admin` и значение, побайтово
совпадающее с `MINIO_ROOT_PASSWORD` (сверено по sha256 13.08.2026). А складывает он туда
записи разговоров. Пока root оставался у потребителя, его нельзя было и ротировать:
ротация ломала бы запись и выдачу разговоров, поэтому HAP-517 ждал именно этой задачи.

Учётку заводит тот же `_docker/init.sh`: пользователь `MINIO_TELEPHONY_ACCESS_KEY` с
политикой `telephony-ari` на бакеты из `MINIO_TELEPHONY_BUCKETS`. Права ýже, чем у CRM, и
это не осторожность ради осторожности, а список того, что реально делает клиент
(`workers/file_service/minio_client.py`): `bucket_exists` → `s3:ListBucket`, `fput_object`
→ `s3:PutObject` + multipart, плюс `s3:GetObject` — записи забирает STT-воркер, которому
эти же ключи уезжают в задании.

🔴 **`s3:DeleteObject` не выдан сознательно.** Удаления объектов в коде телефонии нет
вовсе, а запись разговора — ПДн и единственный экземпляр. Право удалить её не нужно тому,
кто её создаёт.

🔴 **Создания бакетов тоже нет, и это меняет поведение.** Клиент при первой загрузке
делает `make_bucket`, если бакета не оказалось. Под root это молча создавало бакет с
опечаткой в имени вместо ошибки — так и появилась путаница `record` / `records`
(в `deploy/.env` телефонии `MINIO_BUCKET=record`, а в коде воркеров имя `records`
захардкожено; бакета `records` в хранилище нет). Под узкой учёткой промах по имени станет
внятным `AccessDenied` — это то, чего мы хотим. Расхождение чинится на стороне
`telephony-ari`, а не расширением политики.

**Ключи в `.env` руками не пишутся** — источник тот же, Credentials Store папки `crm`
(`minio-telephony-access-key`, `minio-telephony-secret-key`). ⚠️ У этой пары два конца:
те же значения лежат в credential'е `telephony-ari-staging-env` папки `telephony`, откуда
их получает сам сервис. Ротация меняет **оба** — порядок в `jenkins-infra/DEPLOY.md` §10.

## Получение Access key / Secret key

Для нового сервиса — не руками в консоли: аккаунт, заведённый кликами, исчезнет при
пересоздании стека и не будет виден в ревью. Заводите его в `_docker/init.sh` по образцу
CRM (пользователь + своя политика на свои бакеты), а значения доставляйте выкаткой.

Если ключ всё же нужен разово (разбор инцидента, миграция данных):

1. Открыть веб-консоль (`:9001`), войти под `MINIO_ROOT_USER`.
2. Access Keys → создать ключ.
3. Регион уже задан через `MINIO_REGION` (`kz-ala-dev`) — в консоли менять не нужно.

⚠️ Регион менять на работающем хранилище нельзя без согласования: клиенты S3 подписывают
им запросы, и подпись разъедется у всех, кто уже настроен.

## Доступ к консоли

По умолчанию консоль слушает все интерфейсы — как было раньше. Если хост виден за пределами
доверенной сети, безопаснее закрыть её и ходить туннелем:

```bash
# в .env
MINIO_CONSOLE_BIND=127.0.0.1
# с рабочей машины
ssh -L 9001:127.0.0.1:9001 prog@<хост>
```
